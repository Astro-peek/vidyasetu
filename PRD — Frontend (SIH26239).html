PRD — Frontend: Scholarship & Fellowship Management System (SIH26239)

Stack: React 18 + TypeScript, Vite, Supabase JS (auth only), REST client to the Express API Version: 1.0 (MVP) | Owner: Frontend workstream

1. Purpose & Goals

A role-based web app where administrators configure schemes, applicants apply through forms generated from configuration, and officers/committees review applications with AI signals and rule results side by side.

Goals

  1. Every scheme-specific screen (form, documents list, workflow actions) is rendered from backend configuration, not hardcoded.
  2. The scrutiny workspace shows document, extracted fields, AI flags, rule results and history in one view.
  3. AI output is always presented as assistive and overridable.
  4. A clear, credible end-to-end demo: Scheme A, then Scheme B, then a live third scheme.

Non-goals (MVP): native mobile app (SIH26238 covers student-facing mobile), offline mode, multilingual chatbot, public analytics site.

Separate interfaces: the same React app ships two distinct shells: an Applicant Portal (simple, mobile-first) and a Staff/Admin Portal (dense, desktop-first), selected by role after login, matching the PS requirement for separate applicant and administrator interfaces.

4. Screen Requirements

4.1 Auth

  • Email + password (Supabase); email verification; password reset; session refresh handling; idle timeout warning.
  • Applicant self-registration. Staff accounts are created by the admin (no public role selection).

4.2 Scheme Builder (Admin) — core differentiator

A stepper/tabs editor bound to the config JSON (draft versions only):

  1. Meta: name, code, source reference, effective dates.
  2. Form designer: add sections and fields (text, number, date, select, radio, checkbox, textarea, file); set label (EN/HI), required, validation (min/max/regex), conditional visibility (showIf), drag-reorder.
  3. Documents: type, mandatory/optional, formats, size, validity days.
  4. Eligibility rules: visual builder for nested AND/OR groups (field, operator, value, source clause). Includes a rule tester: enter sample values and see rule-by-rule result.
  5. Consistency checks: map form field to document-extracted field with match type.
  6. Workflow (visual editor, required): React Flow canvas. Drag to add states, draw edges for transitions, click an edge to set allowed roles/conditions, click a node to set SLA, notifications and terminal/start flags. Node positions are saved into workflow.layout. Live validation panel (exactly one start state, no unreachable or dead-end non-terminal states, every transition has a role) mirrors the backend /validate. Templates: start from another scheme's workflow. Read-only view when published.
  7. Selection & post-selection: seats, quotas (e.g. PVTG sub-quota), preference boosts (e.g. girls/Divyangjan/PVTG), weighted criteria, committee and interview stages; post-selection follow-ups (joining report, progress report, renewal) with schedule and acceptance deadline.
  8. Notifications: event → template → channel.
  9. Review & publish: JSON diff against the previous version, validation errors from /validate, submit for approval. Approver (different user) sees diff and approves/publishes.

Requirements: live preview of the applicant form; unsaved-changes guard; autosave draft; read-only view for published versions; clone-to-new-version.

4.3 Applicant: Dynamic Application

  • GET /schemes/:id/form returns the definition. The <DynamicForm> renderer builds fields, a Zod schema and conditional logic from it.
  • Multi-step by section, autosave draft, progress indicator, per-field errors.
  • Document step: one upload slot per configured requirement, with drag-drop, format/size checks client-side (server re-validates), preview, replace (versioning), and upload progress.
  • After upload, show AI pre-check status (processing, ready, issues found) with plain-language hints ("page appears cropped") so applicants can fix problems before submitting. These are suggestions, not verdicts.
  • Review & submit screen, and confirmation with application ID.

4.4 Applicant: Status & Deficiency

  • Status timeline (from /timeline), current stage, and expected SLA where configured.
  • Deficiency card: list of requested items, due date, targeted re-upload or field edit, submit response. Only the requested items are editable.
  • Notification center (in-app) with unread badge.

4.5 Scrutiny Queue (Officer)

  • Server-side table: scheme, state, submitted date, SLA countdown/breach badge, AI flag count/severity, assignee.
  • Filters: scheme, state, flag type, priority, deficiency status, "assigned to me". Saved filters, bulk assign (admin).

4.6 Scrutiny Workspace (Officer) — demo centrepiece

Three-pane layout:

  • Left: application data, and a documents list with status chips.
  • Centre: document viewer (zoom, rotate, page nav) with the extracted fields panel beside it: value, confidence bar, form-value comparison, mismatch highlighting, and edit/confirm with a mandatory reason on override.
  • Right tabs: Rules (rule-by-rule pass/fail with expected vs actual and source), AI Flags (evidence, confirm/dismiss), History (audit timeline).
  • Action bar: allowed transitions come from workflow config (Raise deficiency, Mark eligible, Mark ineligible, Forward). Each requires a reason. The deficiency composer has structured item pick-list plus remarks.
  • Labels: "AI-assisted", never "verified/authentic". Low-confidence fields are visually flagged and require an officer's confirmation.

4.7 Committee Workspace

  • Ranked shortlist per scheme with score breakdown (from configured criteria), applicant summary, and document access.
  • Record decision + remarks, and an override with reason when the decision differs from the rank. Final decisions are clearly human-attributed.
  • Interview stage (where configured): panel members enter scores/remarks per candidate, and the merit list recomputes from the configured weights. Quota and preference effects are shown transparently (why a candidate is ranked where they are).

4.8 Analytics Dashboard

Cards and charts: volume by scheme, stage funnel, average processing time, deficiency reasons, SLA breaches, AI flag counts. Aggregates only for ministry role, with no personal data. Date and scheme filters, and CSV export of aggregates.

4.9 Audit Timeline (shared component)

Vertical timeline: time, actor (user / system / AI), action, from→to state, reason, expandable evidence. Reused in the officer, admin and applicant views (applicant sees a filtered subset).

4.10 Admin Users

User list, create staff, assign role, deactivate.

4.11 Applicant: Award & Fellowship (post-selection)

Award offer with accept/decline before the deadline; countdown for deadlines (e.g. admission window); joining/admission form; follow-up tasks (progress report, renewal) with due dates and status; disbursement status list (read-only); all statuses use the shared timeline.

4.12 Admin: Post-Selection Tracker

Table of awardees by scheme/stage/deadline, filters for overdue follow-ups, drill-in to review a follow-up (approve or raise deficiency, using the same components as scrutiny).

4.13 Institution Verifier

List of applicants linked to the user's institution, view the submitted joining/admission details, confirm or query. No access to other institutions' data or unrelated documents.

4.14 Finance Officer

Simple form/table to record disbursement status per awardee and period. Clear label "status record only, no payment is made here".

4.15 Grievances / Help

Applicant and institution: raise a ticket (category, optional linked application), see thread and status. Staff: inbox with filters, assign, reply, close.

4.16 Reports

Pick report type, scheme and date range, preview, export CSV/XLSX/PDF (Hindi text must render correctly in exports).

4.17 Language Switch

EN/HI toggle in the header of both portals, persisted to the profile. No hardcoded strings, and layouts must tolerate longer Hindi text.

5. Dynamic Form Renderer Contract

type FieldDef = {
  key: string; type: 'text'|'number'|'date'|'select'|'radio'|'checkbox'|'textarea';
  label: Record<string,string>; required?: boolean;
  options?: {value:string; label:Record<string,string>}[];
  validation?: { min?:number; max?:number; regex?:string; maxLength?:number };
  showIf?: { field:string; op:string; value:any } | null;
};
  • buildZodSchema(fields) produces validation, and evaluateShowIf drives conditional fields (hidden fields are excluded from the payload).
  • Unknown field types fall back to a safe "unsupported field" notice, and never crash the page.
  • Renderer components are unit-tested against fixtures for NFST-like and NOS-like configs.

6. State, Data & Error Handling

  • API client wrapper (fetch/axios) attaches the JWT, sets X-Correlation-Id, and normalizes errors {code,message,details}. On 401 it refreshes the session once, then redirects to login.
  • TanStack Query keys per resource. AI job status is polled every 3–5 s until terminal, then stops.
  • Every screen has explicit loading (skeletons), empty, error (retry), and forbidden states.
  • Mutations use optimistic updates only for low-risk actions. Transitions and decisions wait for the server. Use Idempotency-Key on submit/transition.
  • Toasts for success/failure. Confirmation dialogs for irreversible actions (submit, reject, publish).

7. UX, Accessibility & Performance

  • WCAG 2.1 AA target: keyboard-navigable flows, visible focus, labelled inputs, ARIA for dialogs/tabs/tables, colour contrast, and never colour-only status (icon + text).
  • Responsive from 360 px (applicant flows, since users may be on low-end phones); staff screens optimised for desktop ≥ 1280 px.
  • Low-bandwidth: route-level code splitting, lazy-load PDF viewer and chart libraries, image compression before upload where safe, target initial JS < 250 KB gzip for the login/applicant shell.
  • Consistent design tokens, and light theme first, with dark theme optional.
  • Plain-language microcopy. Full English + Hindi for both portals (UI strings and config labels), Noto Sans Devanagari loaded with a fallback stack, lang attribute set on the document, and test with long Hindi strings and mixed-script data.

8. Security (Frontend)

  • No secrets in the bundle. Tokens kept in Supabase's session storage handling, with no manual token copying to other stores.
  • Render all user/document/AI-derived text as plain text (React default escaping), and never dangerouslySetInnerHTML.
  • Document URLs are requested on demand (short-lived signed URLs), and not cached in state longer than their expiry.
  • Client-side role gating is UX only. Do not assume it is security.

8.1 Deployment (Vercel)

  • Vite build deployed to Vercel, with vercel.json SPA rewrite (/(.*) → /index.html) so React Router deep links work on refresh.
  • Env vars: VITE_API_BASE_URL (Render API), VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY. No other secrets.
  • Preview deployments call the same API. The backend CORS allow-list must include the preview URL pattern.
  • The Render API may cold-start, so show a friendly "waking up the server" state on the first request and retry with backoff.
  • Route-level code splitting keeps the applicant shell small (see section 7).

9. Acceptance Criteria

  1. An admin builds Scheme A and publishes it. The applicant form appears with no frontend code change.
  2. Scheme B (different fields, documents, rules, workflow) works in the same UI unchanged.
  3. Rule tester and officer workspace show rule-by-rule results with source references.
  4. Officer can view a document beside extracted fields and confidence, override with a reason, and raise a structured deficiency.
  5. Applicant receives a notification, resolves the deficiency, and sees an updated timeline.
  6. Committee sees the ranked shortlist and records decisions.
  7. Audit timeline reconstructs the whole journey.
  8. Keyboard-only walkthrough of applicant submit succeeds, and Lighthouse accessibility ≥ 90 on key pages.
  9. All screens have loading, empty, and error states.
  10. Workflow built visually in React Flow saves, validates, and drives the officer's action buttons with no code change.
  11. The whole applicant journey and a full officer review can be completed in Hindi, with no untranslated strings on key screens.
  12. Post-selection works: award acceptance, joining verification by an institution user, a follow-up submission, and disbursement status visible.
  13. Applicant and staff experiences are visibly separate portals.

11. Decisions & Remaining Questions

Decided: English + Hindi both; visual workflow editor included; Vercel hosting; two separate portals.

Working defaults (change any time):

  1. Look and feel: a clean, neutral government-style UI driven by a single theme-token file, so branding can be swapped later. Use placeholders instead of official emblems or logos.
  2. Mobile: responsive web for the MVP (applicant flows work from 360 px). Dedicated mobile app is out of scope (SIH26238).
  3. Hindi: first-pass translations in one locale file (hi.json) plus a small glossary of key terms (scheme, deficiency, scrutiny, etc.). Strings are marked "draft translation" until a Hindi-speaking teammate reviews them.
