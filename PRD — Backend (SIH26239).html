PRD — Backend: Scholarship & Fellowship Management System (SIH26239)

Stack: Node.js, Express.js, Supabase (Postgres, Auth, Storage, Realtime), Gemini API Version: 1.0 (MVP) | Owner: Backend / Rules / AI workstreams

1. Purpose & Goals

Build a scheme-agnostic administration engine for MoTA scholarships and fellowships. Scheme differences (eligibility, documents, workflow, selection) live in versioned configuration data, not code.

Goals

  1. Two materially different schemes (NFST, NOS) run on one engine with zero code changes.
  2. Deterministic rules decide eligibility; Gemini only assists with unstructured documents; humans make final decisions.
  3. Every important action is auditable (append-only).
  4. Async document processing so AI jobs never block the API.

Non-goals (MVP): Pre-/Post-Matric schemes (state-implemented via NSP/state portals; the engine should be able to onboard them later), production NSP/PFMS/DigiLocker integration, blockchain integrity, predictive rejection models, authoritative certificate validation, native mobile backend.

3. Architecture (Modules)

Express API ─ auth/rbac middleware ─ controllers
   ├─ schemes      (config CRUD, versioning, publish)
   ├─ applications (lifecycle, dynamic payload validation)
   ├─ documents    (upload, classify, versions)
   ├─ rules        (evaluator, explainable output)
   ├─ workflow     (state machine, transitions, SLA)
   ├─ ai           (Gemini client, prompts, extraction pipeline)
   ├─ selection    (merit scoring, committee decisions)
   ├─ notifications(templates, channels, events)
   ├─ audit        (append-only writer)
   └─ analytics    (aggregates)
Worker process (pg-boss): ai.process_document, sla.scan, notify.send

The API and worker are separate entry points, deployed from one repo. Cross-module calls go through service functions, and every state change goes through workflow.transition(), which writes the audit event in the same DB transaction.

Rules

  • audit_events is append-only: a DB trigger rejects UPDATE/DELETE, and app-role permissions revoke them. Optional prev_hash/hash chain (SHA-256) for tamper evidence.
  • AI signal, rule result and human decision are stored in separate tables and never merged.
  • Published scheme_versions are immutable. Applications pin to the version they were submitted under.

6.1 What the official MoTA pages imply for the config model

Observed at tribal.nic.in/ScholarshiP.aspx and dbttribal.gov.in/AllScheme.aspx (treat every number as to be verified against guideline PDFs before it becomes a rule value):

  • Selection differs structurally: NFST is merit-ranked on Master's marks with preference for girls, Divyangjan and PVTGs; NOS uses an expert-committee interview-based merit list with a PVTG sub-quota; Top Class uses Class XII marks. So selection must support seats, quotas, preference boosts, weighted criteria and an interview stage (panel scores).
  • Reference lists: Top Class eligibility depends on a list of notified premier institutes, and the page itself shows two different counts (246 vs 265). This is exactly why lists and rules carry source_ref + effective_from and are versioned (reference_lists, operator in_ref_list).
  • NOS post-selection: the awardee has a fixed window (stated as 2 years) to secure foreign admission, so post-selection needs deadline timers and reminders. Disbursement goes via Indian Missions/MEA, while NFST uses bank linkage, so disbursements.channel differs by scheme.
  • Institution role is real: existing portals have a university verification module and university queries.
  • Existing portals also lean on DigiLocker, UMANG and Aadhaar-linked flows. We model these as adapters, not live integrations (see 10.1).

7. Rules Engine

  • Operators: == != < <= > >= in not_in in_ref_list between exists; groups all / any / not, nestable.
  • Input: form_data plus verified extracted values. Output per rule: {id, passed, actual, expected, source}, plus an overall result (eligible, ineligible, needs_review when required data is missing).
  • Pure, side-effect-free functions with unit tests (target: 100% operator coverage).
  • Re-evaluated on submit, on resubmission, and on officer edits to verified fields.

8. Workflow Engine

  • The state machine is loaded from scheme_versions.config.workflow. transition(appId, to, actor, reason, evidence) checks: the transition is allowed, the role is permitted, and the current state matches (optimistic lock on updated_at).
  • On every transition: update state, write the audit event, enqueue notifications and set the SLA timer, all in one transaction.
  • sla.scan runs every 15 minutes, flags breached applications, notifies the scheme admin, and writes an sla_breach audit event.
  • Deficiency loop: officer raises structured items → state deficiency → applicant resubmits specific items → back to under_scrutiny. Full history retained.

8.1 Post-Selection & Fellowship Management

The problem statement explicitly includes post-selection/fellowship management, so it is a first-class module:

  • Award offer → acceptance: selected applicants accept or decline within a configured deadline. Non-response triggers reminders, then escalation to the admin.
  • Joining/admission confirmation: applicant submits details, the institution_verifier confirms. For NOS-like schemes, a countdown to the admission deadline runs, with reminder notifications.
  • Follow-ups from config (postSelection.followUps): progress reports, renewals, and other periodic submissions, generated on schedule by a worker job (followups.schedule), reviewed by officers, using the same workflow, deficiency and audit machinery as applications.
  • Disbursement ledger: authorised finance_officer records status per period (pending/processed/failed, reference). MVP only records and displays status. Real PFMS/bank/Mission integration is an adapter, out of scope.
  • Grievances/helpdesk: applicant or institution raises a ticket (optionally linked to an application), staff reply in a thread, statuses and SLA apply. Existing portals carry large per-scheme grievance loads, so this directly supports the "repeated correspondence" problem.

9. AI Service (Gemini)

Pipeline (job ai.process_document, triggered on upload):

  1. Fetch the file from Storage, send it to Gemini (inline for small files, Files API for large ones) with a document-type-specific prompt and a JSON response schema.
  2. Request: doc_type classification, extracted fields, per-field confidence (0–1), quality flags (blurry, cropped, missing pages, rotated), plus the text evidence each field came from.
  3. Validate output with Zod. On failure, retry once with a repair prompt; otherwise mark extraction_failed and route to human review.
  4. Store in document_extractions. Run consistency checks (form vs extracted) and create ai_flags.
  5. Low confidence (below configurable threshold, default 0.75) or any conflict → needs_review. Never auto-reject.

Guardrails

  • GEMINI_API_KEY is server-side only, and prompts contain no more PII than needed.
  • Treat document text as untrusted: instruct the model to ignore instructions embedded in documents, and ignore extra keys in the output.
  • Rate limit and retry with backoff on 429/5xx. Record model name and prompt version with each result.
  • The UI must label results "AI-assisted screening", not "verified/authentic".
  • Use synthetic or authorized documents only. Free-tier Gemini usage may be used for model improvement, so use a paid tier or approved arrangement before any real applicant data.
  • Duplicate signals (MVP): identical file hash, same Aadhaar-like/ID field across applications (hashed), same name+DOB+scheme.

10.1 Registration, Identity & Integrations (feasible scope)

  • Registration: native applicant registration via Supabase Auth (email + phone OTP). Staff accounts are created by admins. Applicant profile stores only fields the schemes need.
  • Identity adapter: IdentityProvider interface (verifyIdentity, fetchDocument) with a LocalProvider for the MVP and stub adapters for DigiLocker and NSP-style SSO behind feature flags. We do not claim live integration, since these need government onboarding/credentials.
  • Import API: lets an existing portal push applications into this system in bulk or one at a time, showing the "administration layer that complements existing infrastructure" positioning.
  • PFMS/bank/Mission disbursement: adapter interface, mocked for demo.

10.2 Localization (English + Hindi)

  • profiles.preferred_language; notification templates exist in both languages and the send language follows the recipient's preference.
  • Publish validation: every applicant-visible string (form labels, options, document names, rule messages, template text) must have both en and hi, or publish is blocked.
  • Gemini prompts and the evaluation dataset must include bilingual (Hindi/English) documents and Devanagari text. Report the accuracy per language.
  • PDF/XLSX exports use a Devanagari-capable font (e.g. Noto Sans Devanagari). Storage is UTF-8 throughout.

11. Security & Privacy

  • Verify the Supabase JWT on every request. Deny by default. Rate limit auth-adjacent and upload routes (express-rate-limit), plus helmet and strict CORS allow-list.
  • Upload validation: MIME sniffing (not just extension), size limits, an allow-list of formats, randomised storage paths, and AV scan hook (stub for the MVP).
  • Documents are served only via short-lived signed URLs, issued after an authorization check. Each issuance is audited.
  • Secrets in environment variables only. Never log document contents or full PII.
  • Scheme config changes need approval (maker-checker: creator ≠ approver).
  • Retention: configurable, no invented period. Pending confirmation from official requirements.
  • Test for IDOR, role escalation, malicious uploads, and prompt injection in documents.

13. Acceptance Criteria

  1. Create NFST and NOS via API/config only, both pass through submit → scrutiny → deficiency → shortlist.
  2. A third scheme is created live with no code change or redeploy.
  3. Rule evaluation returns rule-by-rule explainable output with source references.
  4. Gemini extraction produces stored fields, confidence and flags; low confidence never auto-rejects.
  5. Audit replay reconstructs the full application history; UPDATE/DELETE on audit rows fails.
  6. Unauthorized cross-user access attempts return 403/404 in automated tests.
  7. A labelled synthetic dataset yields reported metrics: field accuracy, deficiency precision/recall, rule test pass rate, reported separately for English and Hindi documents.
  8. NFST and NOS run end-to-end (including their different selection setups: preferences/quota/interview), and the live third scheme is built from official Top Class scheme data.
  9. Post-selection works: acceptance, joining verification by an institution user, a scheduled follow-up, and a disbursement status entry, all audited.
  10. Publishing a scheme with a missing Hindi label is blocked.
